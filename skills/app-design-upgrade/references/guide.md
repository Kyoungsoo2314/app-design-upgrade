# 내 앱 디자인 업그레이드

## AI 진단부터 HTML 시안 비교와 실제 적용까지

버전: 1.0 | 작성일: 2026-09-09

이 문서는 바이브코딩으로 만든 앱의 디자인을 개선할 때 AI에게 전달하는 공통 작업 지침입니다. 특정 업종이나 프레임워크에 한정하지 않습니다. 앱을 이해하고 적합한 디자인을 추천한 뒤, 별도 HTML 시안을 비교하고 선택한 디자인을 실제 앱에 적용하도록 안내합니다.

## 1. 사용 방법

1. 작업 중인 앱을 AI 코딩 도구에서 엽니다.
2. 이 문서를 첨부하거나 전체 내용을 전달합니다.
3. 아래 시작 요청을 입력합니다. 앱 위치는 현재 작업 폴더로 알 수 있다면 따로 적지 않아도 됩니다.
4. AI가 만든 시안을 열어보고 선택하거나 수정을 요청합니다.
5. 마음에 드는 시안이 확정되면 실제 앱 적용을 요청합니다.

### 시작 요청

> 이 문서를 기준으로 내 앱을 진단하고 가장 적합한 디자인 개선 방향을 추천해줘. 추천 이유를 쉽게 설명하고, 실제 앱을 수정하기 전에 별도 HTML 시안으로 보여줘. 비교할 가치가 있는 방향이 여러 개면 시안을 비교하고 선택할 수 있게 해줘. 아직 실제 앱에는 적용하지 마.

원한다면 다음 정보도 덧붙이세요. 모두 작성할 필요는 없습니다.

- 주로 사용하는 사람과 가장 자주 하는 업무
- 가장 불편한 화면
- 원하는 개선: 읽기 쉽게, 입력을 빠르게, 모바일에서 편하게, 분위기를 세련되게 등
- 주로 사용하는 기기
- 유지하고 싶은 색상, 로고, 화면 구성

디자인 용어를 몰라도 됩니다. “글씨가 작다”, “한눈에 안 들어온다”, “버튼을 찾기 어렵다”처럼 말하면 됩니다.

### 시안을 보고 요청하는 예시

> A안으로 가되 글자를 조금 키우고, B안의 검색 영역을 가져와줘. 수정한 HTML 시안을 다시 보여줘.

> 두 안 모두 정보가 너무 많아 보여. 자주 쓰는 작업이 먼저 보이는 방향으로 다시 제안해줘.

> 수정된 A안으로 확정할게. 기존 기능을 유지하면서 실제 앱에 적용하고 검증해줘.

## 2. AI 실행 프롬프트

이 절부터 8절까지는 AI가 따라야 하는 작업 지침입니다. 사용자의 현재 요청과 제약을 우선하며, 이 문서는 작업 순서와 판단 기준으로 사용합니다.

### 역할과 목표

당신은 기존 앱의 코드와 사용자 업무를 이해하고 디자인을 개선하는 제품 디자이너이자 프론트엔드 엔지니어입니다.

사용자는 디자인과 개발 용어에 익숙하지 않을 수 있습니다. 도구 이름보다 화면이 어떻게 좋아지고 업무가 어떻게 편해지는지 먼저 설명하세요. 직접 관찰한 사실, 추정, 제안을 구분하세요.

진행 순서는 다음과 같습니다.

```text
앱 이해와 진단
    ↓
디자인 방향과 도구 추천
    ↓
별도 HTML 시안 제작
    ↓
사용자 비교·선택·수정
    ↓
선택한 디자인의 실제 적용
    ↓
기능·화면 검증과 디자인 규칙 기록
```

진단과 추천을 마치면 별도 시안 제작까지 진행하세요. 단계마다 반복해서 진행 허락을 요청하지 마세요. 실제 앱에 적용하기 전에는 사용자의 시안 선택과 적용 요청을 확인하세요. 시안 제작만 요청했다면 시안을 제공하고 선택을 기다리세요.

### 1단계: 앱 이해와 현재 디자인 진단

- 접근 가능한 프로젝트 설명, 코드, 의존성 정보와 실제 화면을 확인하세요.
- 누가, 어떤 기기에서, 어떤 일을 가장 자주 하는지 파악하세요.
- 현재 잘된 점과 유지할 요소도 찾아주세요.
- 정보 배치, 글자 크기, 버튼, 입력 흐름, 표, 그래프, 모바일 화면을 점검하세요.
- 프로젝트에 기존 디자인 시스템이 있다면 우선 존중하세요.
- 실제 화면이나 코드를 볼 수 없다면 확인한 범위를 밝히고, 필요한 최소 정보만 요청하세요. 보지 않은 화면을 확인했다고 말하지 마세요.
- 이미 파악할 수 있는 내용을 다시 묻지 마세요. 목표가 불분명할 때만 결과에 큰 영향을 주는 질문 1~3개를 하세요.

결과는 다음 순서로 간단히 설명하세요.

1. 이 앱의 사용자와 핵심 업무
2. 유지하면 좋은 점
3. 개선 효과가 큰 문제 최대 5개
4. 먼저 개선할 대표 화면 1~2개와 선정 이유

### 2단계: 개선 방향과 적합한 도구 추천

앱의 목적에 맞는 디자인 방향을 먼저 정하고 도구는 그 방향을 구현하는 수단으로 선택하세요.

- 업무용 앱: 빠른 탐색, 반복 입력, 비교하기 쉬운 정보 배치와 상태 구분을 우선하세요.
- 콘텐츠·교육 앱: 읽기 흐름, 탐색, 학습 진행과 미디어 가독성을 우선하세요.
- 브랜드·홍보 사이트: 브랜드와 실제 제품을 보여주는 이미지, 메시지와 주요 행동의 연결을 우선하세요.
- 게임·창작 도구: 조작 피드백, 몰입감, 도구 배치와 성능을 우선하세요.

다음 기준으로 후보를 평가하세요.

| 기준 | 확인할 질문 |
|---|---|
| 업무 적합성 | 사용자가 가장 자주 하는 일을 쉽게 만드는가? |
| 가독성·접근성 | 글자, 대비, 키보드 조작과 터치 조작이 적절한가? |
| 기술 호환성 | 현재 프레임워크와 버전에 무리 없이 적용할 수 있는가? |
| 일관성 | 기존 화면과 자연스럽게 연결할 수 있는가? |
| 유지보수 | 다음 기능을 추가할 때도 쉽게 수정할 수 있는가? |
| 적용 부담 | 화면 수정 외에 프레임워크 전환이나 큰 의존성 변경이 필요한가? |

기존 도구만으로 개선하는 방법도 포함하세요. 검토할 가치가 있는 후보 2~3개를 비교하고 추천 조합 하나를 고르세요. 추천하지 않는 후보는 이 앱에 맞지 않는 이유를 설명하되, 해당 도구 자체가 나쁘다고 단정하지 마세요.

라이브러리의 버전 호환성, 라이선스, 설치 조건 등 바뀔 수 있는 정보는 적용 전에 공식 문서에서 확인하세요. 확인하지 못한 부분은 미확인으로 표시하세요. 유행이나 별점만으로 추천하지 마세요.

“이 도구가 유명합니다” 대신 “검색과 상태 필터를 같은 위치에 배치하고 입력창을 통일하는 데 적합합니다”처럼 설명하세요.

### 3단계: 별도 HTML 시안 제작

추천한 디자인을 실제 앱에 적용하기 전에 사용자가 브라우저에서 볼 수 있는 시안을 만드세요.

- 프로젝트 내부의 별도 시안 폴더에 저장하고 운영 화면·코드·데이터와 구분하세요.
- 첫 시안은 대표 화면 1~2개로 범위를 제한하세요. 전체 앱을 여러 버전으로 구현할 필요는 없습니다.
- 비교 가치가 있으면 기본 2안을 만드세요. 방향이 명확하면 1안과 그 이유를 설명하세요. 3안 이상은 구체적인 차이가 있거나 사용자가 원할 때 제안하세요.
- 색상만 바꾸지 말고 정보 배치, 화면 밀도, 탐색 방식 등 의미 있는 차이를 보여주세요.
- 모든 안에 같은 가상 데이터와 업무 시나리오를 사용하세요.
- 현재 앱의 메뉴명, 필드, 지표 정의와 주요 업무 흐름을 반영하세요. 의미가 달라지는 용어 변경은 별도 제안으로 표시하세요.
- 표·그래프에는 비교가 가능한 현실적인 가상 값, 긴 이름, 여러 상태를 넣으세요.
- 실제 저장·삭제·전송 없이 주요 검색, 필터, 상세 보기, 입력 흐름을 체험할 수 있게 하세요.
- 시연용 동작과 실제로 구현하지 않은 동작은 비교 페이지나 제공 설명에서 구분하세요. 작동하지 않는 버튼을 완성 기능처럼 제시하지 마세요.

가능하면 HTML 파일을 직접 열어 실행되도록 만드세요. 여러 파일이나 로컬 서버가 필요하면 AI가 실행하고 접속 링크를 제공하세요. 외부 리소스나 인터넷 연결이 필요한 경우 알려주세요. 운영용 데이터와 API에 시안을 연결하지 마세요.

여러 시안은 `index.html` 비교 페이지에서 각각 열어볼 수 있게 구성하세요. 각 안에는 중립적인 이름, 주요 차이, 장단점, 적용 부담을 표시하세요. “추천” 표시는 이유와 함께 한 안에만 붙이세요. 현재 화면을 보여줄 수 있다면 식별정보를 가리거나 가상 데이터로 재현하여 함께 비교하세요.

시안에서 선택 버튼을 제공한다면 선택 상태가 화면에 드러나게 하세요. 그 선택이 대화 중인 AI에게 자동 전달되지 않는 환경에서는, 사용자가 전달할 선택 문구를 함께 보여주세요. 버튼 클릭만으로 실제 앱이 변경되는 것처럼 표현하지 마세요.

HTML은 화면 구성과 상호작용을 검토하는 시안입니다. 최종 구현에서 사용할 라이브러리와 다르게 표현한 부분은 알리고, 실제 적용 전에 재현 가능성을 확인하세요.

### 4단계: 비교·선택·수정

시안 링크와 함께 다음 내용을 설명하세요.

1. 각 안에서 무엇이 달라졌는지
2. 어떤 사용자와 업무에 더 적합한지
3. AI의 추천안과 이유
4. 적용 부담: 스타일 위주 수정 / 화면 구조 수정 / 의존성 변경 필요
5. 선택 가능한 다음 행동: 한 안 선택, 부분 조합, 수정 요청, 현재 디자인 유지

사용자가 “깔끔한 쪽”처럼 모호하게 선택하면 필요한 부분만 확인하세요. “A안 메뉴 + B안 그래프”처럼 부분 조합을 허용하세요. 수정 요청은 HTML에 반영하고 다시 보여주세요.

이 단계에서는 사용자의 선택을 기다리세요. 시안을 골랐다는 이유만으로 기능 삭제, 데이터 구조 변경, 외부 서비스 연결까지 승인받았다고 해석하지 마세요. 사용자가 선택과 함께 적용을 요청하면 반복 승인 없이 다음 단계로 진행하세요.

### 5단계: 실제 앱 적용

- 선택한 시안과 사용자의 수정 사항을 기준으로 구현 범위를 정리하세요.
- 기존 프로젝트 지침과 코드 스타일을 따르고, 현재 변경 사항을 보존하세요.
- 복구 가능한 백업이나 버전 관리 상태를 확보한 뒤 작업하세요. 사용자에게는 기술 용어보다 무엇을 복구할 수 있는지 설명하세요.
- 기존 프레임워크와 도구를 우선 활용하세요. 새 의존성은 필요한 것만 추가하세요.
- 정적 HTML을 그대로 붙이는 데 그치지 말고 실제 데이터, 이벤트, 입력 검증, 로딩·오류 상태와 연결하세요.
- 기존 계산식과 업무 규칙은 유지하세요. 별도 기능 개선이 필요하면 디자인 작업과 구분해 설명하세요.
- 기본 버튼, 입력창, 상태 표시, 표, 그래프 등 반복 요소에 공통 규칙을 적용하세요.
- 작은 화면에서도 업무를 수행할 수 있게 하고, 키보드 포커스·입력 레이블·아이콘 설명을 확인하세요.

### 6단계: 검증과 기록

검증은 변경 범위에 맞게 수행하세요. 기존 테스트가 있으면 관련 항목을 실행하고, 중요 업무 흐름을 직접 확인하세요.

- 실제 화면을 승인한 시안과 비교하세요. 차이가 필요했다면 이유를 설명하세요.
- 주 사용 기기의 데스크톱 화면과 모바일 화면을 확인하세요.
- 긴 텍스트, 많은 항목, 빈 데이터, 로딩, 입력 오류와 요청 실패 상태를 점검하세요.
- 그래프는 축, 단위, 범례, 수치와 데이터 의미가 유지되는지 확인하세요.
- 검색, 입력, 수정 등 대표 업무를 안전한 테스트 데이터로 확인하세요.
- 빌드와 필요한 기능 검증을 실행하고, 실행한 검사와 미실행 검사를 구분하세요.
- 글자·색상·간격·버튼·상태·표·그래프 규칙을 프로젝트 안에 짧게 기록하세요. 기존 디자인 문서가 있으면 중복 문서를 만들지 말고 갱신하세요.
- 프로젝트에 수정 기록 규칙이 있으면 따르세요.

완료 보고에는 변경 내용, 실행 화면 링크, 실제 검증 결과와 남은 문제를 포함하세요. 확인하지 않은 기능이나 운영체제에서의 동작을 검증 완료라고 말하지 마세요.

## 3. 시안의 공통 디자인 원칙

- 앱 전체에서 글자 크기, 간격, 모서리, 버튼 높이와 색상 의미를 일관되게 적용합니다.
- 여백은 읽기와 조작을 돕는 만큼 사용하고, 업무용 화면을 불필요하게 길게 만들지 않습니다.
- 카드와 그림자를 남용하지 않습니다. 관련 정보는 구분선과 정렬로도 묶을 수 있습니다.
- 상태는 색상뿐 아니라 글자나 아이콘으로도 구분합니다.
- 익숙한 명령에는 적절한 아이콘을 사용하되, 의미가 불분명하면 이름과 설명을 제공합니다.
- 금액과 수량은 단위와 자릿수를 일관되게 표시합니다.
- 애니메이션은 변화와 피드백을 이해하는 데 필요한 경우에만 사용합니다. 숫자를 읽거나 반복 작업을 하는 데 방해되지 않게 합니다.
- 큰 글자, 진한 그림자, 화려한 배경이 모든 앱의 품질을 높인다고 가정하지 않습니다.
- 참고 서비스의 분위기를 활용하더라도 앱의 목적과 기존 브랜드를 우선합니다.
