# 내 앱 디자인 업그레이드

기존 앱의 사용자와 업무를 이해하고, 적합한 디자인을 별도 HTML로 검토한 뒤 선택한 안을 실제 앱에 적용한다. 사용자 언어로 설명하며 라이브러리 이름보다 화면과 업무의 변화를 먼저 설명한다.

## 실행 범위

- “논의만”, “추천만” 요청이면 그 범위에서 멈춘다.
- 일반적인 디자인 개선 요청이면 진단, 추천, 별도 HTML 시안 제공까지 진행한다. 실제 앱 적용은 선택과 적용 요청을 확인한 뒤 진행한다.
- 이미 시안과 적용 범위를 승인했다면 반복 승인 없이 적용과 검증을 진행한다.
- 구체적으로 지정한 작은 디자인 수정은 불필요한 다중 시안 없이 요청 범위에 맞게 수행한다.
- 디자인 선택을 기능 삭제, 데이터 구조 변경, 외부 서비스 연결이나 공개 배포의 승인으로 확대하지 않는다.

## 1. 앱 진단

프로젝트 지침, 의존성, 실제 화면과 주요 업무를 확인한다. 사용자·기기·빈번한 작업, 유지할 장점, 개선 우선순위 최대 5개를 정리한다. 목표를 추정할 수 없을 때만 핵심 질문 1~3개를 한다. 화면을 볼 수 없다면 코드 검토와 실제 관찰을 구분한다.

## 2. 방향과 도구 추천

업무 적합성, 가독성, 접근성, 현재 버전과의 호환성, 유지보수와 수정 부담으로 비교한다. 기존 도구 유지도 후보에 포함한다. 참고 목록이 필요할 때 [공식 가이드](references/guide.md)의 4절을 읽고, 선택 후보의 최신 조건은 공식 문서에서 확인한다.

추천할 가치가 있는 후보 2~3개와 최종 추천 하나를 제시한다. 현재 디자인 체계를 우선 활용하며 특정 라이브러리나 프레임워크 전환을 강제하지 않는다. 업무용 앱에는 탐색·입력·비교 효율을, 브랜드·콘텐츠·게임에는 해당 목적을 우선한다.

## 3. 독립 HTML 시안

시안 제작 전에 [시안 비교와 선택 기록](references/proposals.md)을 읽는다. 프로젝트 안의 별도 폴더에 대표 화면 1~2개를 만든다. 기존 시안을 덮어쓰기보다 구분되는 버전 폴더를 사용한다.

- 비교가 유용하면 기본 2안, 적합한 방향이 명확하면 1안과 이유를 제시한다.
- 모든 안에 같은 가상 데이터와 대표 업무를 사용한다. 색상 외에 정보 밀도·배치·탐색 방식 등 실질적인 차이를 보여준다.
- 실제 저장·삭제·전송이나 운영 API 연결 없이 검색·필터·상세 보기 등 대표 동작을 체험하게 한다.
- 가능하면 직접 열리는 HTML로 제공한다. 서버가 필요하면 실행하여 URL을 제공하고 외부 의존성을 밝힌다.
- 여러 안은 index.html에서 비교하고 각각 열 수 있게 한다. 선택 결과가 AI에게 자동 전달되지 않으면 사용자가 전달할 선택 문구를 표시한다.
- 제공 전에 실제 렌더링, 데스크톱·모바일, 주요 시연 동작을 확인한다. 테스트 데이터로 긴 글자·빈 상태도 확인한다.

사용자에게 링크, 각 안의 차이, 추천 이유, 적용 부담을 설명한다. 시안을 제공하고 선택을 기다린다. 부분 조합과 수정 요청은 새 시안에 반영한다.

## 4. 선택한 안 적용

선택한 시안, 수정 요청과 적용 승인을 기록한다. 승인이 불명확하면 실제 앱 수정 전에 최소한으로 확인한다. 기존 작업과 기능을 보존하고 복구 가능한 상태를 확보한 뒤 적용한다. HTML을 실제 데이터·이벤트·검증·로딩·오류 처리에 연결한다.

## 5. 검증과 기록

승인한 시안과 실제 화면을 비교하고 관련 빌드·주요 업무·모바일·키보드·오류 상태를 확인한다. 지표의 의미와 계산식은 디자인 변경으로 바꾸지 않는다. 변경 범위에 맞는 검증만 수행한다.

기존 문서가 있으면 그곳에 색상·글자·간격·버튼·상태·표·그래프 규칙을 기록한다. 프로젝트 수정 기록 규칙을 따른다. 완료 보고에는 실행 링크, 변경 내용, 실제 검증과 미확인 범위를 포함한다.

## 참고 자료 사용

- 상세 진행 기준, 도구 목록과 사용자 요청 예시가 필요하면 [공식 가이드](references/guide.md)의 관련 절만 읽는다.
- 비교 페이지의 내용 구성과 선택 상태 기록에는 [시안 비교와 선택 기록](references/proposals.md)을 사용한다.
- 특정 플러그인, 유료 서비스, 별도 에이전트는 필수 조건이 아니다. 접근할 수 없는 코드·화면·실행 결과를 확인했다고 보고하지 않는다.
